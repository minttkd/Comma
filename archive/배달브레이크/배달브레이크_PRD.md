# 배달브레이크 PRD

차민상·안강원 / 창의프로젝트

---

## 1. 개요

**배달브레이크**는 배달의민족·쿠팡·무신사에서 결제를 시도하는 순간, 그 소비가 필수품인지 충동구매인지를 AI가 그때그때 판단하고, 그중에서도 실제로 이번 달 재정에 타격을 줄 수 있는 소비에만 개입하는 Android 접근성 서비스 기반 앱이다.

기존 가계부 앱이 "이미 쓴 돈"만 사후에 보여주는 데 그치는 반면, 배달브레이크는 결제 직전 시점에 개입한다. 다만 모든 소비를 감시·차단하는 방식이 아니라, 필수품으로 보이는 소비는 아예 건드리지 않고, 재정적으로 의미 있는 순간에만 선택적으로 말을 거는 것을 핵심 설계 원칙으로 삼는다.

---

## 2. 배경 및 문제 정의

> 재정적으로 여유가 없는 20대(학생·사회초년생) 자취생이, 배달의민족·쿠팡·무신사에서 반복적으로 충동구매를 하면서 본인이 세운 소비 계획과 무관하게 지출이 누적되고, 월말에 재정적으로 후회하는 문제를 해결한다.

- 토스 등 기존 가계부 앱은 "이미 쓴 돈"만 사후에 보여줄 뿐, 결제하려는 순간에는 아무 도움을 주지 못한다.
- 배달앱·쇼핑앱의 UX(세일 알림, 래플, 무료배송 임계값, 심야 배달 등)는 구조적으로 충동구매를 유도한다.
- 다만 "모든 소비에 개입하는" 접근은 사용자에게 피로감을 주고 앱 이탈(삭제)로 이어질 위험이 크다 — 사용자는 먹고 싶은 것을 먹고 사고 싶은 것을 사기 위해 돈을 번다. 서비스는 이 전제를 침해하지 않아야 한다.

---

## 3. 목표 / 비목표

**목표**
- 결제 시점에 AI가 매 건을 판단해, 필수품 소비는 건드리지 않고 충동구매 가능성이 있는 소비만 걸러낸다.
- 걸러진 소비 중에서도 실제로 "이번 달 재정에 타격이 되는" 소비에만 개입해, 개입 빈도와 체감 마찰을 최소화한다.
- 개입이 발생해도 사용자의 최종 결정권을 침해하지 않는다(강제 차단 없음).

**비목표**
- 모든 충동구매를 100% 차단하는 것이 목표가 아니다.
- 실시간 은행 연동이나 실제 결제 차단 기능 구현은 이번 범위에 포함하지 않는다(모의 데이터로 대체).
- 배달의민족·쿠팡·무신사 외의 앱 지원은 이번 범위에 포함하지 않는다.

## 4. 타겟 사용자

**주 타겟**: 20대, 재정적으로 여유가 없는 학생·사회초년생 자취생. 대학생(용돈·알바) 또는 입사 1~3년차 사회초년생으로, 혼자 살면서 생활비를 처음 스스로 관리하는 사람들.

**페르소나**
- **김지수(27세)**: 입사 2년차 사회초년생, 독립 초반. 평일 밤 배달 야식, 주말 쿠팡·무신사 쇼핑 중 충동구매가 잦다.
- **이수민(22세)**: 대학교 3학년, 자취. 용돈·과외 알바비로 생활하며 사실상 정기 소득자. 시험기간 스트레스로 배달 야식, 무신사 세일 알림에 취약하다.

## 5. 범위

### 5-1. 대상 앱(고정)
- 배달앱: 배달의민족
- 쇼핑앱: 쿠팡, 무신사

### 5-2. 대상 사용자 판별
- 장기간 계좌 입출금 내역으로 정기소득 여부를 하드컷으로 판별한다. 월급, 고정 용돈, 일정한 시급·요일로 반복되는 알바 수입까지 "정기 소득"으로 인정한다.
- 건별로 수입이 들쭉날쭉한 프리랜서형 소득자는 서비스 대상에서 제외한다.
- 경계 사례(입사 직후, 급여일 변동 등)는 사용자가 직접 소득 정보를 입력하는 보조 입력 수단으로 처리한다.

### 5-3. 이번 학기 구현 우선순위
- 배달의민족·쿠팡을 먼저 접근성 서비스로 검증하고, 무신사는 같은 로직이 확장 가능함을 보여주는 선에서 다룬다.
- 실제 오픈뱅킹·마이데이터 연동은 범위 밖이며, Mock 계좌 데이터로 대체한다.

## 6. 핵심 설계 원칙

| 원칙 | 내용 |
|---|---|
| 쿨다운 금지 | 결제 자체를 강제로 지연시키지 않는다. |
| 최종 결정권은 사용자 | 어떤 개입 화면에서도 사용자가 이탈(X)할 수 있다. |
| 필수품은 원칙적으로 건드리지 않는다 | AI가 필요 소비로 판단한 결제는 기본적으로 트리거 평가 없이 즉시 통과한다. 다만 금액이 크거나 재정위험 상태라면 예외적으로 트리거 평가를 받는다. |
| 선택적 개입 | 트리거 종류를 최소화해, 실제로 재정에 의미 있는 소비에만 개입한다. 개입 횟수에 인위적인 상한은 두지 않는다 — 트리거 조건에 맞으면 그때마다 작동한다. |
| 차단 권한 없음 | 접근성 서비스는 안내·질문만 할 수 있고, 결제를 기술적으로 차단할 권한이 없다. |

## 7. 기능 요구사항

### REQ-1. 온보딩 — 정기소득 판별 및 고정지출 설정
- 계좌 연동 후 정기소득 여부를 하드컷으로 판별한다(경계 사례는 수동 입력).
- 고정지출을 아래 6개 항목으로 통합해 계좌 내역 기반으로 자동 추정하고, 사용자가 확인·수정할 수 있게 한다.
  1. 월세 및 관리비
  2. 공과금(수도·전기·가스) — 최근 3개월 평균으로 추정
  3. 통신비(휴대폰 요금·인터넷)
  4. 식비 및 장보기 고정비(구독형 밀키트, 정기배송 식료품, 정기 식권·카페 지출) — **배달앱(배민) 결제는 제외**
  5. 교통비
  6. 구독 서비스 요금(넷플릭스, 유튜브 프리미엄, 쿠팡 와우, 음원 스트리밍 등)
- 월 여윳돈 = 정기 수입 − 고정지출(위 6항목 합).

### REQ-2. 예산 엔진 — 일일 한도 페이스메이커
```
기본 일일액 B = 월 여윳돈 / 급여 주기 일수
당일 가용액 Q = 남은 여윳돈 / 다음 급여일까지 남은 일수
적용 한도    = min(Q, B × k)     (k = 2.0, 제안값)
```
- 적용 한도를 매 결제 시도마다 재계산한다.
- 남은 여윳돈이 0원 이하가 되면 이후 모든 비필수 결제는 재정위험 전환점 트리거의 대상이 된다.
- 급여일에 남은 적용 한도("예비분")는 다음 달 안전잔고로 이전할지 사용자가 선택한다.

### REQ-3. 계좌 동기화
- 화이트리스트 없이 매번 판단하는 구조이므로, 여윳돈·적용 한도 계산에 필요한 계좌 데이터가 최신이어야 한다.
- 배달의민족·쿠팡·무신사 실행을 감지하는 접근성 서비스 이벤트를 계좌 동기화 트리거로 재사용한다.
- 마지막 동기화로부터 캐시 유효기간(제안: 1시간)이 지났을 때만 백그라운드에서 재동기화하고, 판단 자체는 캐시된 데이터로 즉시 수행한다.
- 실제 오픈뱅킹·마이데이터 API 대신 Mock 데이터 + 가상 응답 지연으로 구현·시연한다.

### REQ-4. 품목 판정 — 화이트리스트 없이 매 결제마다 AI가 판단
- 화이트리스트(사전 등록/학습형 목록)를 두지 않는다.
- 쿠팡·무신사 결제 시도마다 상품명 텍스트를 AI에 전달해 **필요 / 애매 / 충동** 세 범주 중 하나로 판정한다.
- 배달의민족 주문은 품목 판정을 적용하지 않고, 처음부터 "애매/충동" 범주와 동일하게 트리거 평가 대상으로 취급한다(배달은 재량지출로 전제).
- **판정이 "필요"인 결제는 기본적으로 트리거 평가를 건너뛰고 즉시 통과한다.** 다만 결제 금액이 고액 단건 기준에 해당하거나 재정위험 상태(적용 한도 초과·여윳돈 0원 이하로 진입하거나 이미 그 상태)라면 예외적으로 트리거 평가를 받는다(REQ-5 참고).
- 상품명 텍스트는 AI에 데이터 필드로만 전달한다(프롬프트 인젝션 방어).

### REQ-5. 개입 트리거

- **"애매/충동" 판정 결제**: 아래 세 트리거 모두 평가 대상이다.
- **"필요" 판정 결제**: 기본적으로 트리거 평가를 받지 않지만, 결제 금액이 고액 단건 기준에 해당하거나 재정위험 상태(적용 한도 초과·여윳돈 0원 이하로 진입하거나 이미 그 상태)인 경우에는 예외적으로 **재정위험 전환점·고액 단건** 두 트리거만 평가한다. 몰아치기 트리거는 적용하지 않는다.

아래 세 트리거 중 하나라도 해당하면 개입 화면을 띄운다. 개입 발생 횟수에는 상한을 두지 않는다.

| 트리거 | 조건(제안값) |
|---|---|
| 재정위험 전환점 | 이 결제를 승인하면 적용 한도를 초과하거나 남은 여윳돈이 0원 이하로 내려가는 경우 |
| 고액 단건 | 결제 금액이 기본 일일액(B)의 3배 이상 또는 10만 원 이상(둘 중 먼저 해당하는 쪽) |
| 몰아치기 | 짧은 시간(제안: 1시간) 안에 "애매/충동" 판정 결제가 3건 이상 발생 |

- 세 트리거는 OR 조건이다 — 하나라도 해당하면 개입한다.
- 몰아치기 집계 시 "필요" 판정 결제는 카운트에서 제외한다.

### REQ-6. 개입 화면(UI)
- 기본: "결제 계속 / 그만둘게요" 버튼 중심 화면. 아래 화살표로 항변 입력창을 선택적으로 펼칠 수 있다.
- 에스컬레이션: 재정위험 전환점과 고액 단건이 동시에 해당하는 경우에만, 버튼 없이 항변 입력(최대 3회)이 필수인 화면으로 전환한다.
- 항변 프로세스(에스컬레이션 시)
  - AI에 상품명, 금액, 판정 결과, 신호등 상태, 남은 여윳돈, 최근 소명 이력 요약, 사용자 항변 텍스트를 데이터 필드로 전달한다.
  - 매 입력마다 AI가 타당성(통과/불통과), 충동구매 의심도, 판단 이유를 반환한다.
  - 통과 시 오버레이 해제, 3회 불통과 시 승인 경로가 닫히고 오버레이는 유지된다(사용자는 X로만 이탈 가능).
  - 소명 이력 일관성(사유 반복도, 사유-품목 불일치, 후회 연결, 통과율 추세)을 평가해 "반복+후회"가 결합될 때만 의심도를 올린다.

### REQ-7. 결과 기록
| 결과 | 기록 분류 |
|---|---|
| "그만둘게요" 선택, 또는 항변 3회 소진 후 결제 안 함 | 방지 실적 |
| 항변 통과 후 결제 | 소명 승인 결제 |
| X로 이탈 | 자기결정 이탈 |
| 트리거에 걸리지 않은 "애매/충동" 결제, "필요" 판정 결제 | 비개입 기록(리포트용) |

### REQ-8. 사후 회고
- 결제 다음 날, 첫 잠금 해제 전 1탭 만족도 질문("어제 ○○ 구매, 만족하시나요? 👍/👎")을 띄운다. 하루에 여러 건이면 묶어서 표시한다.
- 응답은 REQ-6의 소명 이력 일관성 평가(후회 연결 신호)와 서비스 효과 KPI(후회율)에 활용한다.

### REQ-9. 월말 리포트
- 방지 실적, 소명 승인 결제, 자기결정 이탈 건수를 보여준다.
- 비개입 기록(필요/애매/충동 판정 분포, 심야·시간대 패턴 등)을 패턴 정보로 함께 보여준다 — 실시간으로 개입하지 않은 소비도 자각할 수 있게 하는 역할.

## 8. 사용자 흐름 요약

1. 배달의민족·쿠팡·무신사 실행 감지 → 필요 시 계좌 동기화(REQ-3).
2. 장바구니·결제 준비 화면 진입 → 상품명·금액 추출.
3. 품목 판정(REQ-4): 쿠팡·무신사는 AI 판정, 배민은 판정 없이 애매/충동과 동일 취급.
4. "필요" → 즉시 통과(기록만, REQ-7의 비개입 기록).
5. "애매/충동" → 트리거 평가(REQ-5): 재정위험 전환점 / 고액 단건 / 몰아치기.
6. 트리거 미해당 → 조용히 통과(비개입 기록).
7. 트리거 해당 → 개입 화면(REQ-6): 기본은 버튼 선택, 조건 중첩 시 항변 프로세스.
8. 결과 기록(REQ-7) → 다음 날 사후 회고(REQ-8) → 월말 리포트(REQ-9).

## 9. 아키텍처 개요

기존 구조(WebView+오버레이 프론트엔드 → Kotlin 접근성 서비스+판단 로직 → SharedPreferences 저장)를 유지한다.

- **품목 판정 모듈**: 쿠팡·무신사 결제에서 상품명 텍스트를 AI에 전달해 필요/애매/충동 판정을 받는다. 배민 결제는 이 모듈을 거치지 않는다.
- **예산 엔진**: 여윳돈·기본 일일액·당일 가용액·적용 한도를 결제 시도마다 재계산한다. 고정지출 중 "식비 및 장보기 고정비" 계산 시 배달앱 결제를 제외하는 필터를 둔다.
- **계좌 동기화 모듈**: 앱 실행 감지 이벤트에 연결된 캐시 기반 온디맨드 동기화(REQ-3).
- **트리거 판단 로직**: 품목 판정 결과에 따라 즉시 통과시키거나, 트리거 평가로 진입시킨다.
- **항변 대화 상태 관리**: 에스컬레이션된 결제 시도의 1~3차 질문·답변 상태를 오버레이가 떠 있는 동안 임시로 유지한다.
- **프롬프트 인젝션 방어**: 상품명·항변 텍스트는 시스템 지시가 아닌 데이터 필드로만 AI에 전달한다.
- **사후 회고 스케줄러**: 결제 다음 날 첫 잠금 해제 시점을 감지해 1탭 질문 오버레이를 띄운다.
- **데이터 저장**: SharedPreferences에 품목판정 이력, 여윳돈/고정지출 데이터, 트리거 발생 이력, 소명 이력, 결과 기록(REQ-7), 마지막 계좌 동기화 시각을 저장한다. 화이트리스트 테이블은 두지 않는다.

## 10. 비기능 요구사항

- **응답 속도**: 품목 판정·트리거 평가는 결제 화면이 뜨기 전에 완료되어야 한다(사용자가 결제 버튼을 누른 뒤 눈에 띄는 지연이 없어야 함).
- **보안**: AI에 전달하는 상품명·사용자 입력 텍스트는 전부 데이터 필드로 전달해 프롬프트 인젝션을 방지한다.
- **가용성**: 실제 결제를 기술적으로 차단할 수 없다는 전제를 모든 화면 문구와 로직에 반영한다.
- **데모 환경**: 실제 오픈뱅킹 연동 없이 Mock 계좌 데이터로 전체 플로우가 동작해야 한다.

## 12. 오픈 리스크 / 결정 필요 사항

- **AI 품목 판정의 정확도 의존**: 필요 판정이 잘못되면(실제 충동구매를 필요로 오판) 그 즉시 모든 트리거를 건너뛰므로, 화이트리스트 학습 구조보다 오판의 영향이 더 크다. 판정 정확도 검증이 핵심 리스크다.
- **개입 횟수 상한 없음에 따른 피로도**: 상한을 없앤 만큼, "필요" 판정의 정확도와 트리거 세 개(재정위험·고액단건·몰아치기)의 민감도 설계가 사용자 피로도를 좌우한다. 실기기 테스트에서 트리거 발생 빈도를 모니터링해야 한다.
- **몰아치기 집계 단위**: "애매/충동" 판정 건만 카운트하는 로직이 앱별로 어떻게 동작할지(쿠팡·무신사·배민을 합산할지, 앱별로 따로 셀지) 결정이 필요하다.
- **소명 이력 평가의 일관성**: AI가 "이 소명이 충분히 구체적인가"를 매번 같은 기준으로 판단해야 한다. 통과 기준을 규칙으로 먼저 정의해야 한다.
- **실제 결제를 막을 권한이 없다는 한계**: 항변 3회 소진 후에도 결제를 강제로 차단할 수 없다 — 발표에서 이 설계 의도("숙고 유도, 차단 아님")를 분명히 해야 한다.
- **계좌 연동의 실시간성 한계**: 앱 실행 시점 캐시 갱신이라 결제와 정확히 같은 순간의 계좌 상태를 보장하지 않는다. 실제 연동 대신 Mock 데이터로 시연한다는 전제를 명확히 한다.
