# 쉼표 PRD

차민상·안강원 / 창의프로젝트

---

## 1. 개요

**쉼표**는 배달의민족·쿠팡·무신사에서 결제를 시도하는 순간, 그 소비가 필수품인지 충동구매인지를 AI가 그때그때 판단하고, 그중에서도 이번 달 재정에 타격을 줄 수 있는 소비에만 짧게 멈춰 세우는(쉼표를 찍는) Android 접근성 서비스 기반 앱이다.

기존 가계부 앱은 "이미 쓴 돈"을 사후에 보여주는 데 그친다. 쉼표는 결제 직전에 개입한다. 다만 모든 소비를 감시·차단하지 않는다. 필수품, 특히 직접 해 먹는 식료품은 따로 떼어둔 식비 예산에서 처리해 건드리지 않고, 하루 한도를 넘기는 재량 소비나 평소와 다른 큰 소비에만 선택적으로 말을 건다. 개입이 뜨면 그만두기는 버튼 하나로 쉽고, 결제를 이어가려면 AI가 던지는 질문에 답하며 스스로 다시 생각해봐야 한다. 질문의 깊이는 트리거의 심각도에 따라 달라지고, 최종 결정은 사용자가 한다.

---

## 2. 배경 및 문제 정의

> 재정적으로 여유가 없는 20대(학생·사회초년생) 자취생이 배달의민족·쿠팡·무신사에서 반복적으로 충동구매를 하면서, 본인이 세운 소비 계획과 무관하게 지출이 누적되고, 월말에 재정적으로 후회하는 문제를 해결한다.

- 토스 등 기존 가계부 앱은 "이미 쓴 돈"만 사후에 보여줄 뿐, 결제하려는 순간에는 도움을 주지 못한다.
- 배달·쇼핑앱의 UX(세일 알림, 래플, 무료배송 기준 금액, 심야 배달 등)는 구조적으로 충동구매를 유도한다.
- 다만 "모든 소비에 개입하는" 접근은 피로감을 주고 앱 삭제로 이어진다. 사용자는 먹고 싶은 것을 먹고 사고 싶은 것을 사기 위해 돈을 번다. 서비스는 이 전제를 침해하지 않아야 한다.

---

## 3. 목표 / 비목표

**목표**
- 결제 시점에 AI가 매 건을 판단해, 필수품은 건드리지 않고 충동구매 가능성이 있는 소비를 걸러낸다.
- 식비(직접 해 먹는 재료)를 별도 예산으로 떼어, 필요한 장보기가 배달·쇼핑과 같은 한도를 두고 경쟁하지 않게 한다.
- 하루 한도를 넘기거나 평소와 다른 큰 소비, 몰아서 사는 소비에만 개입한다.
- 개입이 뜨면 "확인 버튼 한 번"으로 넘어가지 못하게, 결제 전에 AI 질문으로 한 번 더 생각하게 한다. 질문의 깊이는 상황에 맞게 조절해 피로도를 관리한다.
- AI는 판정하지 않고 질문으로 마음을 돌리도록 돕는다. 최종 결정권은 사용자에게 있다(강제 차단 없음).

**비목표**
- 모든 충동구매를 100% 차단하는 것.
- 실제 은행 연동이나 결제 차단 기능 구현(이번 범위에서는 Mock 데이터로 대체).
- 배달의민족·쿠팡·무신사 외의 앱 지원.
- 외식·오프라인 결제에 대한 실시간 개입(계좌 동기화로 사후 반영만 한다).

## 4. 타겟 사용자

**주 타겟**: 20대, 재정적으로 여유가 없는 학생·사회초년생 자취생. 대학생(용돈·알바) 또는 입사 1~3년차 사회초년생으로, 혼자 살면서 생활비를 처음 스스로 관리하는 사람들.

**페르소나**

- **이수민(22세)**: 대학교 3학년, 자취. 용돈·과외비로 생활하는 사실상 정기 소득자. 시험기간 스트레스로 배달 야식을 자주 시키고, 무신사 세일 알림에 약하다.

## 5. 범위

### 5-1. 대상 앱
- 배달앱: 배달의민족
- 쇼핑앱: 쿠팡, 무신사

### 5-2. 대상 사용자 판별
- 장기간 계좌 입출금 내역으로 정기소득 여부를 하드컷으로 판별한다. 월급, 고정 용돈, 일정한 시급·요일로 반복되는 알바 수입까지 "정기 소득"으로 인정한다.
- 건별로 수입이 들쭉날쭉한 프리랜서형 소득자는 서비스 대상에서 제외한다.
- 경계 사례(입사 직후, 급여일 변동 등)는 사용자가 소득 정보를 직접 입력하는 보조 수단으로 처리한다.

### 5-3. 전제
- 식비는 정기구독(밀키트 구독, 정기배송 등) 없이 **마트 장보기, 쿠팡 식료품, 외식**으로만 나간다고 가정한다.

### 5-4. 이번 학기 구현 우선순위
- 배달의민족·쿠팡을 먼저 접근성 서비스로 검증하고, 무신사는 같은 로직이 확장 가능함을 보여주는 선에서 다룬다.
- 실제 오픈뱅킹·마이데이터 연동은 범위 밖이며 Mock 계좌 데이터로 대체한다.

| 개입 횟수 상한 없음 | 트리거 조건에 맞으면 그때마다 작동한다. |

## 7. 기능 요구사항

### REQ-1. 온보딩 — 정기소득 판별, 고정지출, 식비 예산
- 계좌 연동 후 정기소득 여부를 하드컷으로 판별한다(경계 사례는 수동 입력).
- **고정지출 5항목**을 계좌 내역에서 자동 추정하고, 사용자가 확인·수정할 수 있게 한다.
  1. 월세 및 관리비
  2. 공과금(수도·전기·가스): 최근 3개월 평균
  3. 통신비(휴대폰 요금·인터넷)
  4. 교통비(대중교통 정기 이용 요금)
  5. 구독 서비스 요금(넷플릭스, 유튜브 프리미엄, 쿠팡 와우, 음원 스트리밍 등)
- **식비 예산**을 REQ-3의 방식으로 자동 산출한다. 사용자가 금액을 직접 입력할 필요는 없다.
- 온보딩 화면에 "첫 달 식비는 추정치로 시작하고, 다음 달부터 실제 기록으로 맞춰요"라고 안내한다.

### REQ-2. 예산 구조와 지출 분류

```
월 여윳돈 = 정기 수입 − 고정지출(5항목) − 식비 예산
```

모든 지출은 아래 세 군데 중 한 곳에서 빠져나간다.

| 지출 | 빠져나가는 곳 | 오늘 누적에 더하는가 | 감지 방식 |
|---|---|---|---|
| 월세·공과금·통신비·교통비·구독료 | 고정지출(이미 떼어둠) | 아니오 | 계좌 동기화 |
| 마트 장보기 | 식비 예산 | 아니오 | 계좌 동기화(가맹점명) |
| 쿠팡 식료품 (AI 판정: 식료품 + 필요) | 식비 예산 | 아니오 | 결제 직전 상품명 판정 |
| 배달의민족 | 여윳돈 | 예 | 결제 직전 감지 |
| 쿠팡 비식료품 · 식료품 중 충동 판정 | 여윳돈 | 예 | 결제 직전 상품명 판정 |
| 무신사 | 여윳돈 | 예 | 결제 직전 감지 |
| 외식 · 카페 · 편의점 | 여윳돈 | 예 | 계좌 동기화(가맹점명) |

- **편의점**은 계좌에 상품명이 찍히지 않아 장보기와 간식을 구분할 수 없으므로 외식·간식(여윳돈)으로 분류한다.
- **식비 예산을 다 쓴 뒤**의 식료품 결제는 초과분을 여윳돈에서 빼고 오늘 누적에 더한다(첫 달 보정 기간 예외는 REQ-3).
- 외식처럼 쉼표가 실시간으로 볼 수 없는 결제는 계좌 동기화 때 반영된다. 예: 점심 외식비는 저녁에 배민을 열 때 동기화되어 오늘 누적에 더해진다.

### REQ-3. 식비 예산 추정과 자동 보정
- **마트**: 계좌 내역의 마트 가맹점 결제 최근 3개월 평균.
- **쿠팡 식료품**: 계좌에는 "쿠팡 n원"처럼 총액만 찍혀 과거 식료품 비중을 알 수 없으므로 아래처럼 보정한다.

| 시점 | 쿠팡 식료품 금액 |
|---|---|
| 첫 달 | 쿠팡 결제 총액(최근 3개월 평균)의 50%를 임시값으로 사용 |
| 2개월째 | 첫 달에 실제로 판정·기록된 쿠팡 식료품 합계 |
| 3개월째 | 실측 2개월 평균 |
| 4개월째부터 | 최근 3개월 이동평균 (마트도 동일하게 매달 갱신) |

- 50%는 근거가 있는 수치가 아니다. "모를 때는 중간값에서 시작한다"는 임시 가정이다.
- 쿠팡을 쓰지 않던 사용자는 임시값을 0으로 둔다.
- **첫 달 보정 기간**: 쿠팡 식료품 결제가 식비 예산을 넘겨도 그 결제에는 재정위험 개입을 띄우지 않고 기록만 한다. 초과분은 실제로 쓴 돈이므로 여윳돈에서 빼고, 이후 배민·무신사 등의 판단에 반영한다.
- **선택 기능 — 쿠팡 주문목록 스캔**: 온보딩에서 사용자가 쿠팡 주문목록을 한 번 열어 스크롤하면, 접근성 서비스가 상품명·금액을 읽고 AI가 식료품만 골라 최근 3개월 금액을 계산한다. 이 경우 임시값 대신 실제 금액으로 시작한다. 주문 기록을 읽는다는 사실을 미리 알리고 동의를 받는다.

### REQ-4. 예산 엔진 — 하루 한도

```
기본 일일액 B = 월 여윳돈 / 급여 주기 일수
당일 가용액 Q = 남은 여윳돈 / 다음 급여일까지 남은 일수
적용 한도    = min(Q, B × k)        (k = 2.0, 제안값)
```

- 적용 한도는 결제 시도마다 재계산한다.
- **오늘 누적**은 그날 여윳돈에서 빠져나간 결제(REQ-2 표의 "예" 항목) 합계다. 고정지출과 식비 예산 안의 결제는 더하지 않는다.
- 남은 여윳돈이 0원 이하가 되면 이후 모든 비필수 결제는 재정위험 전환점 트리거의 대상이 된다.
- 급여일에 남은 여윳돈("예비분")은 다음 달 안전잔고로 이전할지 사용자가 선택한다.
- **홈 화면 신호등**(표시용): 오늘 누적이 적용 한도의 70% 미만이면 초록, 70~100%면 노랑, 100% 초과 또는 여윳돈 0원 이하면 빨강.

**계산 예시**

수입 100만 원, 고정지출 50만 원, 식비 예산 10만 원(마트 4만 + 쿠팡 식료품 임시값 6만)인 사용자의 경우:
- 월 여윳돈 40만 원, 30일 기준 B ≈ 13,300원, 상한 B×2 ≈ 26,700원.
- 10일째: 남은 여윳돈 28만 원, 남은 20일 → Q = 14,000원 → 적용 한도 14,000원.

| 그날의 결제 | 처리 | 오늘 누적 |
|---|---|---|
| 점심 외식 8,000원 | 여윳돈 (저녁 동기화 때 반영) | 8,000원 |
| 쿠팡 계란·우유·두부 18,000원 (식료품 + 필요) | 식비 잔액에서 차감 | 8,000원 (변화 없음) |
| 배민 치킨 23,000원 | 결제 후 누적 31,000원 > 한도 14,000원 → **재정위험 전환점** | 개입 화면(S05) |

### REQ-5. 계좌 동기화
- 배달의민족·쿠팡·무신사 실행을 감지하는 접근성 이벤트를 동기화 트리거로 재사용한다.
- 마지막 동기화로부터 캐시 유효기간(제안: 1시간)이 지났을 때만 백그라운드에서 재동기화하고, 판단 자체는 캐시된 데이터로 즉시 수행한다. 동기화에 실패하면 캐시로 진행하고 홈에 마지막 동기화 시각을 표시한다.
- 동기화된 거래는 가맹점명으로 고정지출 / 마트(식비) / 외식·카페·편의점(여윳돈) / 대상 앱 결제로 분류한다. 대상 앱 결제는 결제 직전에 이미 기록했으므로 중복 반영하지 않는다.
- 실제 오픈뱅킹·마이데이터 API 대신 Mock 데이터 + 가상 응답 지연으로 구현·시연한다.

### REQ-6. 품목 판정 — 화이트리스트 없이 매 결제마다 AI가 판단
- 화이트리스트(사전 등록·학습형 목록)를 두지 않는다.
- 쿠팡·무신사 결제 시도마다 상품명 텍스트를 AI에 전달해 두 가지를 판정한다.
  - **범주**: 필요 / 애매 / 충동
  - **식료품 여부**: 예 / 아니오
- **식료품 + 필요** → 식비 예산에서 차감(REQ-2). 과자·음료 대량 구매처럼 식료품이지만 충동으로 판정된 것은 여윳돈으로 처리하고 트리거 평가를 받는다.
- 배달의민족 주문은 품목 판정 없이 "애매/충동"과 같은 기준으로 트리거를 평가한다(배달은 재량 지출로 전제).
- 판정이 "필요"인 결제는 기본적으로 트리거 평가를 건너뛴다. 다만 고액 단건 기준에 해당하거나 재정위험 상태라면 예외적으로 평가한다(REQ-7).
- AI 응답이 2초 안에 오지 않거나 상품명 추출에 실패하면 "애매"로 간주해 흐름을 멈추지 않는다.
- 상품명 텍스트는 AI에 데이터 필드로만 전달한다(프롬프트 인젝션 방어).

### REQ-7. 개입 트리거

| 트리거 | 조건(제안값) |
|---|---|
| 재정위험 전환점 | 이 결제를 승인하면 오늘 누적이 적용 한도를 넘거나, 남은 여윳돈이 0원 이하로 내려가는 경우 |
| 고액 단건 | 결제 금액이 기본 일일액(B)의 3배 이상 또는 10만 원 이상(둘 중 먼저 해당하는 쪽) |
| 몰아치기 | 짧은 시간(제안: 1시간) 안에 "애매/충동" 판정 결제가 3건 이상 발생 |
| 야식 반복 | 야식 시간대(제안: 22:00~04:00)의 배민 결제가 최근 7일 안에 4번째 이상 |

트리거는 성격에 따라 두 묶음으로 본다.
- **재정 트리거**(재정위험 전환점·고액 단건): "이 결제가 지금 재정에 무리인가"를 본다. 오늘 선을 넘는 순간을 잡는다.
- **행동 패턴 트리거**(몰아치기·야식 반복): "같은 지출이 반복되고 있나"를 본다. 한도 안이지만 쌓이는 습관을 잡는다. 야식은 여윳돈에서 나가므로, 야식 반복은 재정위험으로 번지기 전의 조기 경보 역할을 한다.

야식 반복 카운트 규칙:
- 실제로 결제한 야식만 센다. [그만둘게요]로 멈춘 주문은 세지 않는다.
- 야식 주문에 어떤 트리거로든 개입이 일어나면(재정위험으로 걸린 경우 포함) 카운트를 0으로 초기화한다. 같은 습관에 매일 밤 개입하는 것을 막기 위해서다.
- 야식 시간대와 반복 기준(7일 중 n번)은 설정에서 사용자가 바꾸거나 끌 수 있다(야간 근무 등 생활 리듬 차이 대응).

판정 결과별 적용 범위:
- **애매·충동 판정 결제, 배민 주문**: 재정위험 전환점·고액 단건·몰아치기를 평가하고, 배민 주문은 야식 반복도 평가한다.
- **필요 판정 결제(비식료품)**: 고액 단건 기준에 해당하거나 재정위험 상태일 때만 재정위험 전환점·고액 단건 두 트리거를 평가한다.
- **식료품 + 필요 판정 결제**: 식비 잔액 안이면 오늘 누적에 영향이 없으므로 재정위험 전환점에는 해당하지 않는다. 고액 단건 기준을 넘으면 고액 단건을 평가한다. 식비 잔액을 넘기면 초과분만 오늘 누적에 더해 재정위험 전환점을 평가한다(첫 달 보정 기간 제외).
- 몰아치기 집계에는 "애매/충동" 판정 결제만 센다.
- 네 트리거는 OR 조건이다. 개입 횟수에는 상한을 두지 않는다.

### REQ-8. 개입 화면과 AI 질문 대화 (강도별)

트리거에 걸리면 AI가 판정하는 대신 **질문을 던져 사용자가 스스로 다시 생각하게** 한다. 통과·불통과는 없고, 최종 결정은 사용자가 한다. [결제 계속] 같은 단순 버튼은 두지 않는다. 결제하려면 질문에 모두 답해야 [그래도 살게요]가 나타난다. [그만둘게요]는 처음부터 크게 노출해 언제든 바로 누를 수 있다.

**8-1. 강도 3단계**

| | 가벼움 | 보통 | 강함 |
|---|---|---|---|
| 화면 | S05 (칩형) | S06 (대화형) | S06 (대화형) |
| 질문 수 | 고정 질문 1개("지금 사려는 이유가 뭐예요?") | AI 질문 2개 | AI 질문 3개 |
| 질문 재료 | — | 오늘 상황: 필요한 건지 원하는 건지, 지금이어야 하는지, 대안이 있는지 | 이번 달 전체 영향(급여일까지 하루 얼마로 지내야 하는지) + 과거 기록(같은 품목 구매, 다음 날 "후회돼요" 응답) |
| 답하는 방식 | 이유 칩 선택만(직접 입력 없음): "끼니 대용이에요", "약속이 있어요", "다 떨어졌어요", "한 달치 장보기예요", "그냥 사고 싶어요" | AI가 질문마다 만든 답 칩 2~3개, 직접 입력은 선택 | 답 칩 + 질문 하나는 직접 입력(예: "이번엔 뭐가 다를 것 같아요?") |
| 결정 직전 사실 한 줄 | — | 오늘 기준: "23,000원 · 오늘 한도 17,000원 초과" | 이번 달 기준: "129,000원 · 급여일까지 하루 약 7,500원" |
| AI 호출 | 없음(규칙 처리) | 질문마다 | 질문마다 |
| 다음 날 회고 | "그냥 사고 싶어요" 선택 건 우선 표시 | 일반 대상 | [그래도 살게요] 선택 건 우선 표시 |

- 가벼움은 칩을 고르면 바로 결제가 진행된다.
- 보통·강함은 마지막 질문에 답하면 사실 한 줄과 함께 [그만둘게요](크게) / [그래도 살게요](작게)가 나타난다. 이 사실 한 줄은 AI가 쓰지 않고 계산값으로 고정 표시한다.
- 마지막 답이 이미 결정을 담고 있으면 버튼을 한 번 더 누르지 않게 바로 연결한다. 예: "다음 달에 살게요" 칩 → [그만둘게요] 처리 / "그래도 지금 살래요" 칩 → [그래도 살게요] 처리.
- 화면에 AI 정리 단계는 두지 않는다. 대화가 끝나면 백그라운드에서 한 줄 요약을 만들어 대화 이력에만 저장한다.

**8-2. 강도 결정 순서**

1. **트리거 조합으로 기본 강도를 정한다.**

| 걸린 트리거 / 상태 | 기본 강도 |
|---|---|
| 몰아치기만 / 야식 반복만 / 몰아치기 + 야식 반복 (행동 패턴 트리거만) | 가벼움 |
| 고액 단건만 (식비 예산 안의 식료품 등 오늘 누적에 영향 없는 경우) | 가벼움 |
| 재정위험 전환점 — 오늘 누적이 적용 한도 초과 (단독 또는 행동 패턴 트리거와 함께) | 보통 |
| 재정위험 전환점 + 고액 단건 | 강함 |
| 남은 여윳돈 0원 이하 (이미 그 상태이거나 이 결제로 그렇게 되는 경우) | 강함 |

야식 반복은 강도를 올리지 않는다. 강도는 재정 트리거가 정하고, 야식 반복은 개입을 여는 조건이자 질문 재료로만 쓴다.

2. **필요 판정이면 한 단계 낮춘다.** AI가 "필요"로 판정한 결제가 예외로 트리거 평가를 받은 경우다(최저 가벼움). 이때 문구는 "필요한 소비지만 오늘 한도를 넘어요"처럼 질책 없는 정보형으로 쓴다.
3. **같은 날 반복되면 한 단계 올린다.** 그날 세 번째 개입부터 한 단계 올린다(최고 강함). X로 닫은 뒤 결제 버튼을 눌러 오버레이가 다시 뜬 경우는 새 개입으로 세지 않고, 강도도 올리지 않는다.

**8-3. AI 질문 유형**

AI는 상황(트리거, 상품, 남은 여윳돈·식비 잔액, 과거 기록)과 바로 앞의 답을 보고 아래에서 골라 이어간다. 보통은 1~3번 위주, 강함은 4·5번을 반드시 포함한다.

1. **필요 vs 욕구**: "지금 이게 필요한 거예요, 갖고 싶은 거예요?"
2. **시점**: "오늘 안 사면 어떤 일이 생겨요? 주말까지 미뤄도 괜찮을까요?"
3. **대안**: "식비 예산이 23,000원 남았는데, 장 봐서 해 먹는 건 어때요?"
4. **미래의 나**: "이걸 사면 급여일까지 하루 약 7,500원으로 지내야 해요. 그래도 지금 사야 할까요?"
5. **과거 연결**: "지난달 외투를 두 번 샀고, 한 번은 다음 날 후회된다고 했어요. 이번엔 뭐가 다를 것 같아요?"
6. **패턴(야식 반복)**: "이번 주 네 번째 야식이에요. 지금 배가 고픈 거예요, 출출한 거예요?"

야식 반복이 재정 트리거와 함께 걸리면 질문 1은 돈(한도·여윳돈), 질문 2는 패턴으로 나눠 쓴다. 결정 직전 사실 한 줄은 숫자가 분명한 금액 쪽을 우선한다. 야식 반복만 걸린 가벼움에서는 이유 칩 위에 사실 한 줄("이번 주 네 번째 야식이에요 · 4번 합계 51,000원")을 보여주고, 칩은 [진짜 배고파요] [습관처럼 시켰어요] [공부하느라요] [약속이 있어요]를 쓴다. "습관처럼 시켰어요" 선택은 대화 이력에 남겨 과거 연결 질문의 재료로 쓴다.

**8-4. 예시** (여윳돈 40만 원, B ≈ 13,300원, 10일째 적용 한도 14,000원, 고액 기준 ≈ 4만 원)

| 상황 | 트리거 | 강도 | 대화 흐름 |
|---|---|---|---|
| 무신사 양말·키링·머리끈을 30분 안에 연달아 결제(누적 11,300원) | 몰아치기 | 가벼움 | "그냥 사고 싶어요" 칩 → 결제 진행, 기록 |
| 쿠팡 휴지·세제 26,000원 (필요, 비식료품) | 재정위험 → 필요라 한 단계 낮춤 | 가벼움 | "다 떨어졌어요" 칩 → 결제 진행 |
| 쿠팡 쌀·고기 52,000원 (식료품 + 필요, 식비 잔액 안) | 고액 단건 | 가벼움 | "한 달치 장보기예요" 칩 → 결제 진행 |
| 점심 외식 8,000원 후 배민 치킨 23,000원 | 재정위험 | 보통 | ①"배고픈 거예요, 치킨이 당기는 거예요?" → [치킨이 당겨요] ②"주말까지 미뤄도 괜찮을까요?" → [주말도 괜찮아요] → 그만둘게요로 연결 |
| 밤 11시 무신사 티셔츠·모자·양말 연속 결제(누적 40,900원) | 재정위험 + 몰아치기 | 보통 | ①"필요한 거예요, 세일이라 눈에 띈 거예요?" ②"이번 주에 꼭 입을 일이 있어요?" → 결정 |
| 쿠팡 노트북 충전기 45,000원 (필요, 비식료품) | 재정위험 + 고액 → 필요라 한 단계 낮춤 | 보통 | ①"지금 쓰던 충전기는 어떤 상태예요?" → [고장 났어요] ②"더 저렴한 호환 제품도 괜찮을까요?" → 결정 |
| 무신사 울 코트 129,000원 | 재정위험 + 고액 | 강함 | ①"입을 외투가 없어서예요, 마음에 들어서예요?" ②(직접 입력) "지난달 외투를 두 번 샀고 한 번은 후회했어요. 이번엔 뭐가 다를까요?" ③"급여일까지 하루 약 7,500원으로 지내야 해요. 그래도 지금 사야 할까요?" → 결정 |
| 25일째 여윳돈 −5,000원 상태에서 배민 떡볶이 15,000원 | 여윳돈 0원 이하 | 강함 | ①"지금 많이 배고파요, 스트레스 때문이에요?" ②(직접 입력) "이번 달 남은 5일을 어떻게 보낼 계획이에요?" ③"식비 예산이 23,000원 남았는데 장 봐서 해 먹는 건 어때요?" → 결정 |
| 그날 세 번째 개입, 몰아치기만 | 몰아치기 → 반복으로 한 단계 올림 | 보통 | 칩 1개 대신 AI 질문 2개 |
| 밤 11시 배민 떡볶이 12,000원, 오늘 다른 지출 없음, 이번 주 4번째 야식 | 야식 반복 | 가벼움 | 사실 한 줄 "이번 주 네 번째 야식이에요" + [습관처럼 시켰어요] 칩 → 결제 진행, 야식 카운트 초기화 |
| 점심 8,000원 후 밤 11시 배민 치킨 23,000원, 4번째 야식 | 재정위험 + 야식 반복 | 보통 | ①"오늘 한도를 17,000원 넘어요. 배고픈 거예요, 치킨이 당기는 거예요?" ②"이번 주 네 번째 야식이에요. 주말로 미뤄볼까요?" → 결정, 카운트 초기화 |
| 새벽 1시 배민 회·초밥 세트 45,000원, 4번째 야식 | 재정위험 + 고액 + 야식 반복 | 강함 | ①"4만 원이 넘는 야식이에요. 오늘 특별한 날이에요?" ②(직접 입력) "지난주 야식 뒤에 '후회돼요'라고 답했어요. 오늘은 뭐가 달라요?" ③"결제하면 급여일까지 하루 얼마로 지내야 하는지" → 결정 |
| 밤 11시 배민 결제, 이번 주 3번째 야식, 한도 안 | 없음 | — | 비개입 기록, 야식 카운트만 증가 |

**8-5. 대화 규칙**
- **판단하거나 혼내지 않는다.** 질문은 호기심 있고 공감하는 톤으로만 하고, "충동구매네요" 같은 단정은 쓰지 않는다.
- **숫자는 정직하게.** 남은 여윳돈, 하루 가용액, 식비 잔액 같은 계산값만 쓰고, 과장하거나 죄책감을 자극하는 표현(다크 패턴)은 쓰지 않는다.
- **칩 중심.** AI는 질문마다 답 칩 2~3개를 함께 만든다. 직접 입력은 강함의 질문 하나에만 필수다.
- AI에는 상품명, 금액, 판정 결과, 걸린 트리거와 강도, 남은 여윳돈, 식비 잔액, 최근 대화 이력 요약, 사용자의 답을 데이터 필드로만 전달한다(프롬프트 인젝션 방어).
- 대화 이력의 일관성(같은 이유 반복, 이유와 품목 불일치, 다음 날 후회 응답)은 질문 소재로 쓴다. 특히 강함의 "과거 연결" 질문에 활용한다.
- 다음 질문 생성이 2초 안에 오지 않으면 미리 준비된 기본 질문으로 대신해 흐름을 멈추지 않는다. 첫 질문은 오버레이가 뜨는 동시에 미리 생성해둔다.

**8-6. X 처리**
- 모든 개입 화면에 X를 항상 노출한다(가벼움에서는 보통 크기, 보통·강함에서는 작게).
- X는 오버레이를 닫는다. 닫은 뒤 같은 결제 화면에서 결제 버튼을 누르면 클릭 이벤트를 감지해 오버레이를 다시 띄운다. 대화는 처음부터가 아니라 하던 질문부터 이어가고, 강도는 올리지 않으며 새 개입으로 세지도 않는다.
- 홈 버튼 등으로 앱을 나갔다가 결제 화면에 다시 들어와도 오버레이를 다시 띄운다.

### REQ-9. 결과 기록

| 결과 | 기록 분류 |
|---|---|
| [그만둘게요] 선택 (대화 도중이든 끝난 뒤든) | 방지 실적 (몇 번째 질문에서 마음을 돌렸는지 함께 기록) |
| 가벼움에서 칩 선택 후 결제 | 이유 선택 결제 (선택한 칩 기록) |
| 보통·강함에서 질문에 답한 뒤 [그래도 살게요] | 숙고 후 결제 (강도·답변·요약 기록) |
| X로 닫고 결제 화면을 떠남 | 자기결정 이탈 |
| 트리거에 걸리지 않은 결제, 식비 예산 안의 식료품 결제 | 비개입 기록(리포트용) |

- [결제 계속] 버튼이 없으므로, 개입 이후 결제는 모두 "이유 선택 결제" 또는 "숙고 후 결제"를 거친다.

### REQ-10. 사후 회고
- 결제 다음 날, 첫 잠금 해제 전에 1탭 만족도 질문("어제 ○○ 구매, 만족하시나요? 만족해요 / 후회돼요")을 띄운다. 하루에 여러 건이면 묶어서 표시한다.
- 대상: 이유 선택 결제와 숙고 후 결제 전체. 가벼움에서 "그냥 사고 싶어요"를 고른 건과 강함에서 [그래도 살게요]를 고른 건은 우선 표시한다.
- 응답은 대화 이력에 저장해 다음 대화의 "과거 연결" 질문(REQ-8-3)과 KPI(후회율)에 활용한다.

### REQ-11. 홈 · 월말 리포트
- **홈(S04)**: 오늘 쓸 수 있는 돈(적용 한도 − 오늘 누적)과 신호등, 남은 여윳돈, 급여일까지 남은 일수, **식비 예산 잔액**, 이번 달 방지 실적, 최근 기록, 마지막 동기화 시각.
- **월말 리포트(S10)**: 야식 횟수·금액과 지난달 대비 변화, 방지 실적·이유 선택 결제·숙고 후 결제·자기결정 이탈 건수와 금액, 강도별 마음 돌림 비율, 자주 고른 이유 칩, 식비 예산 사용률, 외식·편의점 지출 합계, 비개입 기록의 판정 분포와 시간대 패턴, 후회율. 다음 달 식비 예산 보정 결과도 함께 보여준다.

## 8. 사용자 흐름 요약

1. 대상 앱 실행 감지 → 필요하면 계좌 동기화(REQ-5), 외식·마트 등 새 거래를 분류해 여윳돈·식비 잔액·오늘 누적 갱신.
2. 결제 준비 화면 진입 → 결제 버튼 위에 투명 가드를 올리고 대기(이 단계에서는 개입하지 않는다). 쿠폰 적용 등으로 금액이 바뀌어도 개입하지 않는다. 사용자가 결제 버튼을 누른 순간 화면을 다시 읽어 상품명·최종 결제금액(쿠폰 적용 후)을 추출한다.
3. 품목 판정(REQ-6): 쿠팡·무신사는 AI 판정, 배민은 판정 없이 애매/충동과 동일 취급.
4. 식료품 + 필요 → 식비 잔액에서 처리(고액이거나 식비 초과면 REQ-7 평가).
5. 그 외 필요 → 고액·재정위험이 아니면 통과.
6. 애매·충동·배민 → 트리거 평가(REQ-7).
7. 트리거 미해당 → 조용히 통과(비개입 기록).
8. 트리거 해당 → 강도 결정(트리거 조합 → 필요 판정이면 −1 → 같은 날 반복이면 +1) → 개입 화면(REQ-8). [그만둘게요] 또는 강도별 대화(가벼움은 이유 칩 선택 후 결제, 보통·강함은 AI 질문 2~3개에 답한 뒤 [그만둘게요]/[그래도 살게요] 선택). X로 닫은 뒤 결제 버튼을 누르면 하던 질문부터 다시 표시(강도 변화 없음).
9. 결과 기록(REQ-9) → 다음 날 사후 회고(REQ-10) → 홈·월말 리포트(REQ-11).

## 9. 아키텍처 개요

기존 구조(WebView+오버레이 프론트엔드 → Kotlin 접근성 서비스+판단 로직 → SharedPreferences 저장)를 유지한다.

- **감지 대상 제한**: 접근성 서비스의 대상 패키지를 배달의민족·쿠팡·무신사로 한정한다.
- **계좌 동기화 모듈**: 앱 실행 감지 이벤트에 연결된 캐시 기반 온디맨드 동기화와 가맹점명 분류(REQ-5).
- **예산 엔진**: 여윳돈·식비 잔액·기본 일일액·당일 가용액·적용 한도·오늘 누적을 결제 시도마다 재계산한다. 고정지출·식비 예산 안의 결제가 오늘 누적에 중복 반영되지 않게 하는 규칙을 포함한다.
- **식비 보정 모듈**: 첫 달 임시값, 보정 기간 처리, 월말 이동평균 갱신, 선택적 주문목록 스캔(REQ-3).
- **품목 판정 모듈**: 쿠팡·무신사 상품명을 AI에 전달해 범주와 식료품 여부를 받는다. 배민 결제는 거치지 않는다.
- **트리거 판단 로직**: 판정 결과와 예산 상태로 REQ-7의 적용 범위를 결정하고 트리거를 평가한다. 야식 반복은 배민 결제 시각과 최근 7일 야식 결제 기록(초기화 시점 이후)으로 판단한다.
- **강도 결정 로직**: 트리거 조합, 필요 판정 여부, 그날 개입 횟수로 강도를 정한다(REQ-8-2).
- **질문 생성 모듈**: 상황과 직전 답을 바탕으로 AI가 다음 질문과 답 칩 2~3개를 만든다. 첫 질문은 오버레이 표시와 동시에 미리 생성하고, 지연 시 기본 질문으로 대체한다.
- **대화 상태 관리**: 강도, 진행 중인 질문 순서, 지금까지의 답변을 저장해 X로 닫았다 다시 열어도 이어서 진행한다.
- **대화 요약(백그라운드)**: 대화가 끝나면 한 줄 요약을 만들어 대화 이력에 저장한다. 화면에는 표시하지 않는다.
- **결제 버튼 가드(개입 시점)**: 결제 화면에서 결제 버튼의 화면 좌표에 접근성 오버레이 창(투명, 버튼 영역만)을 올려 터치를 가로챈다. 터치 시점에 최종 금액을 다시 읽어 판단하고, 개입이 필요 없으면 가로챈 터치를 버튼에 그대로 전달(ACTION_CLICK)한다. 개입 후 [그래도 살게요]나 이유 칩을 고르면 가드를 내리고 사용자가 결제 버튼을 직접 다시 누른다. 버튼 위치를 못 찾으면 클릭 이벤트(typeViewClicked)로 대체하며, 이 경우 간편결제가 이미 시작됐을 수 있다. 앱 밖으로 나가면 0.8초 안에 가드를 내린다.
- **재표시 감지**: X로 닫은 뒤 같은 결제 화면에서 결제 버튼을 다시 누르면(가드 터치) 오버레이를 다시 띄운다.
- **오버레이 터치 차단**: 오버레이가 떠 있는 동안 아래 결제 버튼이 눌리지 않도록 결제 화면 전체를 덮는다.
- **프롬프트 인젝션 방어**: 상품명·사용자 답변은 시스템 지시가 아닌 데이터 필드로만 전달한다.
- **사후 회고 스케줄러**: 결제 다음 날 첫 잠금 해제 시점을 감지해 1탭 질문을 띄운다.

## 11. 비기능 요구사항

- **응답 속도**: 품목 판정·트리거 평가는 결제 화면이 뜨기 전(목표 1.5초 이내)에 끝나야 한다.

- **데모 환경**: 실제 오픈뱅킹 연동 없이 Mock 계좌 데이터로 전체 흐름이 동작해야 한다.

## 13. 오픈 리스크 / 결정 필요 사항

**리스크**
- **재정위험 전환점의 개입 빈도**: 하루 한도가 1~2만 원 수준이라, 점심 외식 후 저녁 배달만 시켜도 한도를 넘는 날이 흔하다. 하루 단위 판단을 유지하기로 했으므로, 실기기 테스트에서 하루 평균 개입 횟수를 모니터링하고 k값·기준을 조정한다.
- **AI 판정 정확도 의존**: 필요·식료품 판정이 틀리면 식비 예산이나 트리거 적용 범위가 잘못 결정된다. 특히 충동성 식료품이 "식료품 + 필요"로 오판되면 감시에서 빠진다.
- **첫 달 식비 추정의 부정확성**: 쿠팡 식료품 임시값 50%는 가정이다. 첫 달에는 여윳돈과 하루 한도가 실제와 다를 수 있다.
- **가맹점 분류 오류**: 마트와 외식, 편의점 구분을 가맹점명에 의존한다. 분류가 틀리면 식비와 여윳돈이 섞인다.
- **외식 반영 지연**: 외식은 계좌 동기화 시점에 반영되므로, 동기화 전에는 오늘 누적이 실제보다 작게 계산될 수 있다.
- **접근성 서비스 동작 미검증**: 세 앱의 결제 화면 텍스트가 접근성으로 읽히는지(웹뷰 여부 등) 실기기·에뮬레이터 검증이 필요하다. 오버레이 위 키보드 입력도 기종별로 확인해야 한다.
- **실제 결제 차단 불가**: 오버레이 재표시로 앱 안에서는 질문을 거치지 않고 결제하기 어렵지만, 기술적으로 완전한 차단은 아니다. 발표에서 설계 의도("숙고 유도, 차단 아님")를 분명히 한다.
- **모든 개입에 질문을 붙인 데 따른 피로도**: 하루 한도 방식이라 개입 빈도가 높은데, 매번 질문에 답해야 한다. 가벼움은 칩 하나, 보통은 칩 위주 질문 2개로 부담을 낮췄지만, 실기기 테스트에서 개입당 소요 시간과 그만두기·이탈 비율을 지켜봐야 한다.
- **칩 선택의 습관화**: 가벼움에서 같은 칩만 반복해서 누르면 효과가 떨어진다. 같은 칩 반복 선택은 대화 이력에 기록하고, 반복 상향 규칙과 회고로 보완한다.
- **야식 기준의 개인차**: 야간 근무자나 늦게 저녁을 먹는 사람에게 밤 주문은 야식이 아니다. 시간대·횟수를 사용자가 바꾸거나 끌 수 있게 하고, "7일 중 4번" 기준은 사용자 인터뷰로 검증한다.
- **AI 호출 증가**: 보통·강함은 질문마다 AI를 호출하므로 응답 지연과 비용이 늘어난다. 가장 빈도가 높은 가벼움은 AI 없이 처리하고, 첫 질문 미리 생성과 기본 질문 대체로 지연을 줄인다.
- **관문이 없다는 한계**: 질문을 대충 넘기고 [그래도 살게요]를 누를 수 있다. 강제성의 성격이 "통과 못 하면 못 산다"에서 "생각을 하고 나서야 산다"로 바뀐 것이며, 효과는 마음 돌림 비율로 검증한다.
- **질문의 유도·왜곡 위험**: AI가 죄책감을 자극하거나 사용자의 답을 왜곡하는 질문을 만들 수 있다. 질문 생성 지침(혼내지 않기, 계산값만 사용)을 프롬프트로 고정하고 샘플 대화를 검수한다.
- **키보드 입력 의존**: 보통·강함은 직접 입력이 필수라, 다른 앱 위 오버레이에서 키보드가 정상 동작하는지가 핵심 경로가 됐다. 실기기 검증이 우선이다.
